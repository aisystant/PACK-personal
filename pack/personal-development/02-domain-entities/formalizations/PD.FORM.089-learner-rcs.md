# Формализация: Role Characterisation Space (RCS) Ученика

## 1. Назначение

### Четыре понятия — четыре разных вопроса

RCS использует четыре термина, которые отвечают на разные вопросы про Созидателя. Без этого различения они кажутся взаимозаменяемыми — но это не так.

| Вопрос | Термин | Пример |
|--------|--------|--------|
| **Из чего состоит Созидатель?** | **Узел** | Организм, Репозитории, Агенты |
| **В каком направлении он растёт?** | **Ось** | Мировоззрение / Мастерство (Пилот); БД / Программа (Машина) |
| **Что счита́ет машина автоматически из событий?** | **bh-характеристика** (bh. = behaviour) | bh.sys, bh.inv, bh.met — 7 метрик Аттестатора |
| **Как Диагност увидит потенциал в диалоге?** | **cp-срез** (cp. = capacity) | cp.rhy, cp.wld, cp.int — 13 срезов Диагноста |

Узел — физический объект. Ось — направление роста. bh-характеристика — непрерывный счёт поведения из событий. cp-срез — точечная оценка потенциала через рубрику. Четыре понятия, потому что четыре разных вопроса.

### Болид-онтология

Для диагностики система «человек + IWE» рассматривается через аналогию **Болида**: Пилот (биологический человек) + Машина (IWE). Созидатель — роль человека, а не этот составной носитель. Пилот, Машина и их рабочая связка развиваются по разным свидетельствам:

| Объект | Как развивается | Кто развивает |
|--------|-----------------|---------------|
| **Пилот** | Тренируется — наращивает Мировоззрение и Мастерство | Человек через программу ЛР |
| **Машина** | Строится — пополняются Pack, Среда, Агенты | Человек при проектировании IWE |
| **Болид** | Обкатывается — пилот и машина притираются в работе | Совместная практика реальных проектов |

**Развитие операционной проекции «человек ↔ IWE»** = развитие Пилота + создание IWE + проверка их совместной способности.

### Узлы Пилота

```
Человек (Пилот):
  Организм                          — тело, ритм, энергия
  Личность:
    Мыслительное мастерство         — картина мира, системные различения ← ЛР
    Прикладное мастерство:
      Мастерство саморазвития       — роль Ученика, M001–M008 ← ЛР
      Мастерство управления IWE     — ОРЗ-ритуалы, экзокортекс, агенты ← ЛР (cp.iwe)
      Мастерство создания IWE       — Pack-дизайн, новые методы, MCP-инструменты ← ЛР (cp.cre)
      Профессиональные методы       — методы предметной области (вне ЛР)
      Прочие прикладные мастерства  — спорт, язык, ремесло и т.д. (вне ЛР)
```

> **ЛР работает на четыре узла:** Мыслительное мастерство, Мастерство саморазвития, Мастерство управления IWE (cp.iwe), Мастерство создания IWE (cp.cre).
>
> Управление и создание IWE — **две независимые оси мастерства среды**. Развиваются параллельно: можно быть Пользователь-3 (уверенный пользователь) и одновременно Разработчик-0 (ещё не начал создавать) или Пользователь-3 + Разработчик-1 (уверенный пользователь + начинающий создатель). Обе оси — **рекомендательные**: используются Портным для контента и рекомендаций, но не блокируют ступень Ученика (см. §5).

### Узлы Машины

```
IWE (Машина):
  Репозитории (БД)                  — Pack и DS-файлы: формализованные знания
  Среда (Программа)                 — VS Code, Git, хуки, конфигурации, протоколы
  Агенты                            — модели + настройки + MCP-инструменты
```

### Оси роста

| Объект | Воздействие → Ось | Что меняется |
|--------|-------------------|--------------|
| **Пилот** | теория → **Мировоззрение** | Как видит себя, мир, роли |
| **Пилот** | методы → **Мастерство** | Что умеет делать устойчиво |
| **Машина** | информация → **БД** | Накопленные формализованные знания |
| **Машина** | инструменты → **Программа** | Среда, скрипты, агентные навыки |

### Петля управления (определение ступени)

Ступень не определяется ни только Аттестатором, ни только Диагностом — нужен **двойной gate**:

```
bh-характеристики (Аттестатор, авто) → сигнал → Диагност (cp-срезы, по запросу) → подтверждение → Ступень
```

1. Аттестатор считает 7 bh-метрик из событий Activity Hub → сигнал «рекомендуемая ступень»
2. Диагност проводит диалог по ≤5 вопросам → оценивает потенциал по cp-срезам → подтверждает или корректирует
3. Итоговая ступень фиксируется только после подтверждения Диагноста

Для ступеней 1–4 достаточно двойного RCS-gate. Ступень 5 — продвинутый результат ЛР и подтверждённая готовность к РР по PD.FORM.003 §5 — дополнительно требует профиля Проактивного и подтверждённого реального изменения по PD.FORM.093 (§5.2). Фактическое начало РР этим расчётом не определяется.

**Зачем двойной gate?** bh-метрики фиксируют частоту и объём поведения (что и сколько делает), но не видят потенциал (глубину понимания, качество мышления, возможность роста). cp-срезы видят потенциал, но не частоту. Только вместе они дают воспроизводимую ступень.

### Два инструмента измерения

| Инструмент | Коды | Когда | Метод | Что измеряет |
|------------|------|-------|-------|--------------|
| **Аттестатор** (WP-310) | **bh.*** | Непрерывно, каждую неделю | SQL по Activity Hub, §12 | Поведение: частота, объём, регулярность |
| **Диагност** (MIM.R.009) | **cp.*** | По запросу, при расчёте ступени | ≤5 вопросов + рубрики §4, аудит артефактов | Потенциал: глубина понимания, качество ОРЗ |

### Проблема и решение

**Проблема.** PD.FORM.003 и PD.FORM.080 описывают ступени Ученика (1 Случайный → 5 Проактивный) как плоские нарративные состояния. При диагностике живого человека решение «ступень = N» не воспроизводимо — два диагноста могут прийти к разным ступеням.

**Решение.** Перейти к **многомерному профилю** по формализму FPF A.19 `U.CharacteristicSpace`. Разделить автоматические bh-метрики (Аттестатор) и диагностические cp-срезы (Диагност). Ступень вычисляется из профиля явным правилом (§5).

**Три эффекта:**
1. **Диагностика воспроизводима.** Алгоритм: bh-сигнал → cp-рубрики → ступень + bottleneck.
2. **Видно слабое звено.** Bottleneck определяет фокус на квартал.
3. **RCS-часть составного gate Д→П** формализована как bh-сигнал + cp-подтверждение; полный gate ступени 5 дополняют две проверки PD.FORM.093 (§5.2).

## 2. Структура RCS: 13 cp-срезов (диагностика Диагноста)

> **Принцип.** Каждый cp-срез диагностирует конкретный узел Созидателя через рубрику 1-5. Срез ≠ узел: узел = физический объект, срез = инструмент измерения потенциала.
>
> **TTL правило.** Четыре стержневых среза `cp.rhy`, `cp.wld`, `cp.skl`, `cp.int` имеют срок действия **6 месяцев** и должны быть свежими для подтверждения текущей ступени или любого повышения. `cp.agt` должен быть свежим только при проверке перехода 4→5. Просроченный стержневой профиль даёт неопределённую текущую оценку и требует повторной диагностики; исторически достигнутая ступень при этом не стирается.

| Код | Срез | Что диагностирует | Узел | Статус |
|-----|------|-------------------|------|--------|
| **cp.rhy** | Ритмичность | Регулярность практики: частота, ритм, восстановление после срыва | Организм | **mandatory** |
| **cp.wld** | Мировоззрение | Зрелость системного взгляда (мировоззренческая дуга FORM.080 §3) | Мыслительное мастерство | **mandatory** |
| **cp.skl** | Мастерство саморазвития | Владение M001–M008: глубина и автоматизм применения | Мастерство саморазвития | **mandatory** |
| **cp.iwe** | Управление IWE | ОРЗ-ритуалы, Pack/DS-структуры, маршрутизация знаний, Week/Month Close | Мастерство управления IWE | informational (рекомендательная ось) |
| **cp.int** | Системное мышление | Применение различений: роль, система, граница, эмерджентность | Мыслительное мастерство | **mandatory** |
| **cp.agt** | Агентность | Доля самоинициированных действий, независимость решений | Поведенческий gate (§5.2) | **transition gate** (только ст.5) |
| **cp.cre** | Создание IWE | Pack-дизайн, MCP-инструменты, расширения протоколов | Мастерство создания IWE | informational (рекомендательная ось) |
| **cp.knw** | Системное знание | Владение SoTA-методами домена | Профессиональные методы | informational |
| **cp.env** | Среда и окружение | Осознанное управление физической и цифровой средой | Среда (IWE.Среда) | informational |
| **cp.auto** | Автопилот | Глубина использования AI-агентов как автопилота | Агенты (IWE.Агенты) | informational |
| **cp.exo** | Экзоскелет | Использование IWE как усилителя мышления, не замены | Среда + Агенты | informational |
| **cp.cult** | Культура и передача | Передача методов и мировоззрения другим | Надсистема (сообщество) | informational |
| **cp.traj** | Траектория и рефлексия | Осознанное управление собственным путём развития | Личность (рефлексия) | informational |

**Стержневые для расчёта ступени:** cp.rhy, cp.wld, cp.skl, cp.int + cp.agt (gate ст.5).
**Информационные (профиль, не блокируют):** cp.iwe, cp.cre, cp.knw, cp.env, cp.auto, cp.exo, cp.cult, cp.traj.

> **Решение v5.0 (17 мая 2026):** cp.iwe и cp.cre — две независимые оси мастерства IWE — переведены из mandatory в informational. Причина: лестница ступеней Ученика (5 нарративных уровней зрелости) и стадии мастерства IWE (две оси × 3 имени: Пользователь 1-3 / Разработчик 1-3) — разные шкалы. Жёсткий gate на cp.iwe смешивал их. Теперь Портной использует cp.iwe и cp.cre как **рекомендательные оси** для контента (см. §6.3). Ступени 1–4 ограничивает стержневой профиль `cp.rhy`/`cp.wld`/`cp.skl`/`cp.int`; `cp.agt` дополнительно блокирует только переход 4→5.

## 3. Квартет каждого среза (по PD.FORM.088 §2)

Каждый cp-срез = четвёрка:

| Элемент | Что фиксируется |
|---------|-----------------|
| **Характеристика** | Свойство системы-человека как аспект внимания |
| **Показатель** | Выбранная шкала и единица измерения |
| **Значение** | Два числа: **сейчас** (моментальное) и **baseline** (устойчивый уровень, сглаживание 4-8 недель) |
| **Потенциал** | Текущий потолок шкалы для данного человека |

**Правило формулировки цели:** любая цель программы ЛР в рамках среза обязана называть, что двигаем:
- «Поднять **baseline** среза cp.rhy с N до M за квартал» → cp.skl/cp.iwe (методы)
- «Расширить **потенциал** среза cp.int с N до M за год» → cp.wld/cp.int (фундаментальное развитие)

Цель, сформулированная через «значение-сейчас», отбрасывается как реакция на шум (PD.FORM.088 §2.1).

## 4. Определения cp-срезов

> **Ограничение MVP:** конкретные шкалы и пороги — draft. Финальная версия со всеми тестовыми заданиями и алгоритмом измерения — следующая итерация (§9 Roadmap).

### cp.rhy — Ритмичность

| Элемент | Значение |
|---------|----------|
| Характеристика | Регулярность практики саморазвития: ритм, частота, восстановление |
| Показатель | Среднее дней/нед практики (скользящее 4-8 нед) + max разрыв |
| Значение (сейчас) | Дней/нед текущей недели |
| Значение (baseline) | Скользящее среднее 4-8 недель |
| Потенциал | Ежедневная практика как стиль жизни, max разрыв ≤1 дня |

**Рубрики baseline-индексов 1-5.**

| Индекс | Дн/нед | Операционные признаки baseline |
|--------|:------:|--------------------------------|
| **1** | ~1-2 | Случайные всплески. Нет паттерна недели. Срывы на месяцы. Восстановление ≥ месяца |
| **2** | ~3 | Пробует регулярность. Минимум 1-2 фиксированных слота в неделю. Срывы 2-3 нед, восстановление 2-3 нед |
| **3** | ~5 | Устойчивый недельный ритм. Срывы короткие (≤2 нед), восстановление ≤1 нед. Практика — привычка, не усилие воли |
| **4** | ~6 | Высокая регулярность. Редкие срывы (≤7 дней). Ритм адаптируется к контексту (командировки, аврал) — не разрушается |
| **5** | ~6.7+ | Ежедневная практика как стиль. Пропуск ≤1-2 дня/мес. Ритм передаётся — способен поддержать другого в построении ритма |

### cp.wld — Мировоззрение

| Элемент | Значение |
|---------|----------|
| Характеристика | Зрелость системного мировоззрения |
| Показатель | Фаза мировоззренческой дуги (FORM.080 §3), индекс 1-5 |
| Значение (сейчас) | Текущая фаза по ответам в диалоге |
| Значение (baseline) | Фаза, устойчиво проявляющаяся 4+ нед в артефактах |
| Потенциал | 5 (системное мировоззрение + agency) |

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Проблемы объясняет внешними обстоятельствами. Нет языка системы/метода. Артефакты: отсутствуют или чисто событийные |
| **2** | Видит внутренние ресурсы: внимание, энергия, ритм. Различает «состояние» и «задачу». В речи: «я собран/не собран», «у меня не было ресурса» |
| **3** | Замечает влияние среды (люди, мемы, пространство). В речи: «окружение тянет», «я попал под влияние». Артефакты: записи о влиянии среды |
| **4** | Описывает задачи через роли, границы, интерфейсы. Различает «я» и «моя роль». В речи: «я как [роль]», «обещание системы». Артефакты: системные разборы ситуаций |
| **5** | Интегрированное системное мировоззрение + agency. Создаёт культурные формы. В речи: «мы как система». Артефакты: наставничество, публикации, инициативы |

### cp.skl — Мастерство саморазвития

| Элемент | Значение |
|---------|----------|
| Характеристика | Глубина и автоматизм применения методов M001–M008 |
| Показатель | Уровень освоения методов: знает / применяет эпизодически / применяет системно / учит других |
| Значение (сейчас) | Применяемые методы текущей недели |
| Значение (baseline) | Устойчиво встроенные методы (6+ нед применения) |
| Потенциал | Все методы ЛР как автоматизированный стиль + способность передать |

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | Методы ЛР (M001-M008) неизвестны или известны формально. Работа по интуиции и привычке. Нет учёта времени, слотов или Day Open/Close |
| **2** | Знает 2-3 метода ЛР. Применяет помидорки или Day Open/Close эпизодически. Держит ритм 2-3 нед, потом срыв. Восстановление — несколько недель |
| **3** | 4-6 методов ЛР применяет устойчиво. Помидорки/слоты как привычка. Day Open/Close регулярно. Восстановление после срыва — ≤1 нед |
| **4** | Полный стек M001-M008 применяется автоматически. Методы встроены в ежедневный режим без напоминаний. Понимает граничные случаи применения |
| **5** | Методы ЛР — стиль жизни. Адаптирует методы под свой контекст. Способен передать метод другому и поддержать его освоение |

### cp.iwe — Управление IWE

| Элемент | Значение |
|---------|----------|
| Характеристика | Владение рабочей средой: ОРЗ-ритуалы, Pack/DS-структуры, маршрутизация знаний, управление памятью, конфигурация агентов |
| Показатель | Зрелость экзокортекса: доля задач через ОРЗ + наличие Pack/DS + активность Week/Month Close |
| Значение (сейчас) | % задач за неделю через ОРЗ |
| Значение (baseline) | Устойчивая доля + зрелые артефакты (WP-контексты, captures, Week/Month Close) |
| Потенциал | 100% значимых задач через ОРЗ + полная IWE-инфраструктура |

**Рубрики baseline-индексов 1-5.**

| Индекс | Операционные признаки baseline |
|--------|--------------------------------|
| **1** | ОРЗ не применяется. Задачи без явного Открытия/Закрытия. Экзокортекса нет (возможно, есть бот как канал). Артефакты случайны и не связаны. Нет WP-контекстов |
| **2** | Open/Close применяются эпизодически (<30% значимых задач). Начата Pack- или DS-структура, слабо заполнена. 1-2 WP-контекста. Day Open/Close — нерегулярно. Week Close — нет |
| **3** | ОРЗ на значимых задачах (>60%). Day Open/Close — регулярно. Pack и DS структурированы по шаблонам. 5+ WP-контекстов. Week Close — регулярно. Memory-файлы обновляются |
| **4** | ОРЗ как норма (>90%). Протоколы «на автомате». Зрелый экзокортекс: Pack с 10+ формализациями, DS с чётким routing. Month Close как ритуал с явным циклом обратной связи. Субагенты применяются |
| **5** | 100% значимых задач через ОРЗ. Свои расширения протоколов, задокументированные для других. Передаёт метод. Экзокортекс — полная инфраструктура: Pack, DS, FMT-шаблоны, staging-канал |

**Имя стадии мастерства IWE — функция ступени Ученика, не cp-индекса.**

cp.iwe-индекс (1-5) измеряет **факт** освоения управления средой по операционным признакам выше. Имя стадии («Пользователь-1», «Разработчик-2» и т.д.) — это **ожидаемое имя на каждой ступени Ученика**, единое для двух осей IWE (cp.iwe и cp.cre). Полная таблица — в §6.3.

Краткая привязка (см. §6.3 для полной таблицы и логики):

| Ступень Ученика | Стадия мастерства IWE |
|:---:|:---|
| 1 Случайный | **Пользователь-1** |
| 2 Практикующий | **Пользователь-2** |
| 3 Систематический | **Пользователь-3 + Разработчик-1** (одновременно — переходная точка) |
| 4 Дисциплинированный | **Разработчик-2** |
| 5 Проактивный | **Разработчик-3** |

> **Source-of-truth:** имена стадий определены **здесь и в §6.3**. Реализация в коде — общий модуль `DS-autonomous-agents/scripts/iwe_stage_names.py`, импортируется `iwe-stage-controller.py` и `render-pilot-guides.py`. **Имя стадии не выводится из cp.iwe-индекса — оно задаётся ступенью Ученика.**

> **Связь со ступенью Ученика — рекомендательная.** На ст.3 Ученика (Систематический) ожидаемый профиль = cp.iwe ≥ 3 (Пользователь-3). Если cp.iwe < 3 — Портной рекомендует подтянуть управление средой. cp.iwe **не блокирует** ступень — это рекомендательная ось.

## 5. Правила вычисления ступени (composition rule)

### 5.1 Двойной RCS-gate (Аттестатор → Диагност)

```
1. Аттестатор рассчитывает bh-сигнал по §12.3 → recommended_stage
2. Диагност проводит диагностику: ≤5 вопросов по cp-срезам → cp-профиль
3. Для ступеней 1–4: подтверждаемая текущими данными ступень = min(recommended_stage, core_cp_floor)
4. Для перехода 4→5 применяется составной gate §5.2
```

**Порядок приоритета для ступеней 1–4:** bh-сигнал не может быть выше cp-профиля. Человек с высокой систематичностью (bh.sys=5), но слабым мировоззрением (cp.wld=2) остаётся на ступени 2.

**Административный старт ≠ подтверждённая текущая ступень.** После зачисления участник входит в учебный нарратив ступени 1 «Случайный» и может выполнять входные задания сразу. Это хранится как состояние участия (`program_participation_status = enrolled`) и `narrative_start_stage = 1`, но само по себе не записывает `current_stage = 1`. Первая подтверждённая текущая оценка требует полного 7-дневного окна bh-наблюдений без разрыва телеметрии и свежих значений всех четырёх стержневых cp-срезов. До этого `current_stage = None`, `stage_evaluation_status = indeterminate`.

### 5.2 Составной gate перехода 4→5: Проактивный и готовность к РР

> **Общая граница программ по активной PD.FORM.003 §5:** ступень 4 — базовое завершение ЛР. Ступень 5 — продвинутое завершение ЛР для тех, кто дорос до Проактивного внутри этой программы, и одновременно готовность/допуск к РР. Gate подтверждает ступень и готовность, но не зачисление и не фактический старт РР.
>
> **Полный тройной gate:** (i) двойной RCS-gate — bh-сигнал + cp-подтверждение (§§5.1–5.2, 12.3); (ii) метрический gate переходного профиля с уверенностью не ниже medium, рассчитанной только по пяти обязательным характеристикам (PD.FORM.093 §§5.4, 7.1); (iii) свежее подтверждение изменения на уровне охвата не ниже 2 (PD.FORM.093 §7.2: confidence ≥ medium, изменение и диагностическая сессия ≤3 месяцев).

**Cp-часть RCS-gate:** для перехода ст. 4 → 5:
- **Стержневой gate:** cp.rhy ≥ 4, cp.wld ≥ 4, cp.skl ≥ 4, cp.int ≥ 4
- **Agency gate:** cp.agt ≥ 4 (устойчивая доля самоинициированных действий)
- **TTL gate:** все blocking cp-срезы диагностированы ≤6 месяцев назад
- **cp.iwe и cp.cre — не в gate.** Используются Портным для рекомендаций (см. §6.3), не блокируют переход.

```python
CORE_CP = ('rhy', 'wld', 'skl', 'int')
def cp_is_fresh(slice_code):
    slice_value = cp.get(slice_code)
    return (
        slice_value is not None
        and type(slice_value.baseline_idx) is int
        and 1 <= slice_value.baseline_idx <= 5
        and slice_value.assessed_at is not None
        and slice_value.assessed_at >= now() - interval('6 months')
        and slice_value.assessed_at <= now()
    )

core_cp_fresh = all(cp_is_fresh(slice_code) for slice_code in CORE_CP)
cp_agt = cp.get('agt')
cp_agt_fresh = cp_agt is not None and cp_is_fresh('agt')
core_cp_known_failure = any(
    cp_is_fresh(slice_code) and cp[slice_code].baseline_idx < 4
    for slice_code in CORE_CP
)
cp_agt_known_failure = cp_agt_fresh and cp_agt.baseline_idx < 4
core_cp_floor = (
    min(cp[slice_code].baseline_idx for slice_code in CORE_CP)
    if core_cp_fresh else None
)
# Количество последовательных полностью наблюдаемых календарных дней,
# заканчивающихся текущим днём; отсутствие событий допустимо, разрыв ingestion — нет.
bh_signal_evaluable = (
    bh_observation_window_days >= 7
    and activity_hub_ingestion_complete IS TRUE
    and type(recommended_stage) is int
    and 1 <= recommended_stage <= 5
)

stage5_cp_gate_status = (
    'not_passed' if core_cp_known_failure or cp_agt_known_failure else
    'indeterminate' if not core_cp_fresh or not cp_agt_fresh else
    'passed'
)
stage5_bh_gate_status = (
    'indeterminate' if not bh_signal_evaluable else
    'passed' if recommended_stage >= 5 else
    'not_passed'
)

stage5_gate_status = (
    'not_passed' if stage5_bh_gate_status == 'not_passed'
        or stage5_cp_gate_status == 'not_passed'
        or form093_metric_gate_status == 'not_passed'
        or form093_real_change_gate_status == 'not_passed' else
    'indeterminate' if stage5_bh_gate_status == 'indeterminate'
        or stage5_cp_gate_status == 'indeterminate'
        or form093_metric_gate_status == 'indeterminate'
        or form093_real_change_gate_status == 'indeterminate' else
    'passed' if stage5_bh_gate_status == 'passed'
        and stage5_cp_gate_status == 'passed'
        and form093_metric_gate_status == 'passed'
        and form093_real_change_gate_status == 'passed' else
    'not_passed'
)
stage5_gate_passed_now = stage5_gate_status == 'passed'

if not bh_signal_evaluable or not core_cp_fresh:
    candidate_stage = None
    stage_evaluation_status = 'indeterminate'
else:
    candidate_stage = 5 if stage5_gate_passed_now else min(recommended_stage, core_cp_floor, 4)
    stage_evaluation_status = 'confirmed'

current_stage = candidate_stage
attained_stage = (
    previous_attained_stage
    if candidate_stage is None
    else max(previous_attained_stage or candidate_stage, candidate_stage)
)

rr_readiness_status = (
    'ready' if current_stage == 5 and stage5_gate_passed_now else
    'revalidation_required' if attained_stage is not None and attained_stage >= 5 else
    'reassessment_required' if stage5_gate_status == 'indeterminate' else
    'not_ready'
)
rr_ready_at_start = current_stage == 5 and stage5_gate_passed_now
```

**Раздельные состояния.** `candidate_stage` и равное ему `current_stage` показывают текущее состояние, подтверждаемое свежими данными; при неполном 7-дневном bh-окне, разрыве телеметрии либо просроченном/неполном стержневом cp-профиле оба равны `None`, а `stage_evaluation_status = indeterminate`. Отдельный `stage5_gate_status` сохраняет различие между непройденным и пока неоцениваемым переходом 4→5. `attained_stage` — монотонно хранимая исторически достигнутая ступень зрелости, а не квалификация; до первой подтверждённой оценки `previous_attained_stage` и `attained_stage` равны `None`. Поэтому истечение TTL или временная просадка может понизить текущую оценку либо сделать её неопределённой, но не отменяет исторически достигнутую ступень. Жизненный цикл ЛР хранит четыре независимых факта: `lr_basic_result_achieved_at` (впервые подтверждена ступень 4), `lr_advanced_result_achieved_at` (впервые подтверждена ступень 5), `lr_program_completed_at` (участник фактически завершил выбранную траекторию) и `lr_completion_stage ∈ {4, 5}` (ступень на момент завершения). Если участник остаётся в программе после ступени 4, завершение можно записать уже на ступени 5. Если он завершил программу на ступени 4, последующее достижение ступени 5 фиксируется как продвинутый milestone и не переписывает исторический факт выпуска.

На момент успешной оценки ступени 5 действует `rr_readiness_status = ready`, но это не бессрочный допуск: перед фактическим стартом РР заново проверяется полный gate, включая TTL блокирующих cp-срезов и свежесть доказательства реального изменения. Истёкшие или просевшие данные дают `revalidation_required`, а не ретроактивное понижение ступени. `rr_started` остаётся отдельным историческим событием и записывается только при `rr_ready_at_start = true`.

### 5.3 Bottleneck

**Bottleneck ступеней 1–4** = cp-срез с минимальным индексом среди четырёх стержневых:

```
bottleneck = argmin(cp.rhy, cp.wld, cp.skl, cp.int).baseline_idx
```

Навигатор и Портной используют bottleneck для фокуса контента на квартал. При подготовке перехода 4→5 низкий `cp.agt` показывается отдельно как **transition blocker**, но не понижает уже подтверждённую ступень 4.

> **cp.iwe и cp.cre не входят в bottleneck**, но Портной отдельно анализирует имена стадий мастерства IWE (Пользователь 1-3 / Разработчик 1-3) и даёт рекомендации по их развитию — см. §6.3.

### 5.4 Информационные cp-срезы не блокируют ступень

cp.iwe, cp.cre, cp.knw, cp.env, cp.auto, cp.exo, cp.cult, cp.traj — **профиль, не ступень**. Они влияют на:
- Рекомендации Навигатора
- Контент Портного (cp.iwe и cp.cre → имена стадий мастерства IWE, см. §6.3)
- Выбор канала (cp.auto → глубина автопилота)

> **Оси мастерства IWE (cp.iwe, cp.cre) — особый случай информационных срезов:** имеют именованные стадии (Пользователь 1-3 / Разработчик 1-3) и маркеры связи со ступенью Ученика. Это рекомендательная двумерная карта развития мастерства среды, отображаемая Портным в персональном руководстве.

## 6. Применение ролями платформы

### 6.1 Диагност (MIM.R.009 / DP.ROLE.042)

**Алгоритм: три фазы, ≤5 вопросов суммарно.**

> **CAT-принцип (Computerized Adaptive Testing):** начало — со **среднего уровня (ст. 3)**, не с ст. 1. Опытных нельзя «сажать в первый класс» — это создаёт трение и не даёт информации. При оценке ≥ 3 → Фаза 2 пропускается; при оценке ≤ 2 → уточнение bottleneck (Фаза 2).
>
> **Два режима:** платформенный (DP.ROLE.042, WP-318) — ответы структурированные (chip/radio 1-5); коучинговый (человек-тренер) — открытые вопросы.

**Фаза 1. Первичный срез** (2-3 вопроса, начиная со ст. 3)

| cp-срез | Якорный вопрос (ст. 3-ориентир) | Рубрика 1-5 |
|---------|--------------------------------|-------------|
| **cp.rhy** | «Как вы ведёте учёт инвестированного времени и есть ли регулярный ритм?» | 1: нет, 2: иногда, 3: еженедельно, 4: ежедневно + трекер, 5: автоматически + артефакты |
| **cp.wld** | «Как принимаете решения — через ценности, системный анализ или интуитивно?» | 1: интуиция, 2: пробую, 3: через мировоззрение, 4: системно, 5: передаю другим |
| **cp.skl** | «Какой метод саморазвития вы можете применить к своей задаче без подсказки и показать результат?» | 1: не назвал, 2: повторяет по шаблону, 3: применяет знакомый метод, 4: выбирает и адаптирует метод, 5: создаёт и передаёт практику |
| **cp.int** | «Приведите пример применения системного мышления к реальной ситуации.» | 1: нет опыта, 2: слышал, 3: базовые различения, 4: системный разбор, 5: формализую |

Если все 4 оценки ≥ 3 → Фаза 2 пропускается.

`cp.skl` оценивается отдельным вопросом: ритм и мастерство могут коррелировать, но один срез не выводится из другого. `cp.agt` запрашивается отдельным пятым вопросом только при проверке перехода 4→5; `bh.agn` остаётся независимым поведенческим сигналом.

**Фаза 2. Уточнение bottleneck** (1-2 вопроса, только если кандидат со значением < 3)

| cp-срез | Уточняющий вопрос |
|---------|-------------------|
| **cp.rhy bottleneck** | «После длинного перерыва (болезнь, аврал) — сколько времени уходит на возврат к ритму?» |
| **cp.skl bottleneck** | «Покажите последнее применение метода: какую задачу решали, почему выбрали этот метод и что изменилось?» |
| **cp.wld bottleneck** | «Приходилось ли объяснять другому важное решение? Через события или через выбор ролей?» |
| **cp.int bottleneck** | «Можешь показать артефакт, где ты использовал системный язык — роль, граница, интерфейс?» |

**Фаза 3. Сверка независимых bh-сигналов** (0 вопросов, автоматически — платформенный режим)

Диагност запрашивает bh-данные из Аттестатора (DP.ROLE.041). `bh.*` не переписывает `cp.*` и не подставляется вместо ответа: совпадение повышает уверенность, расхождение запускает уточняющий вопрос или аудит артефакта. До устранения существенного расхождения оценка остаётся `indeterminate`, а не автоматически повышается.

| bh-сигнал | С чем сверяется | Правило |
|-----------|-----------------|---------|
| `bh.inv` | `cp.rhy` + `cp.skl` | Время — повод проверить ритм и освоение метода, но не доказательство их уровня |
| `bh.sys` + `bh.stb` | `cp.rhy` | Частота и разрывы подтверждают либо опровергают рассказ о ритме |
| `bh.awr` | `cp.wld` + `cp.int` | События рефлексии дают свидетельства для уточнения глубины |
| `bh.agn` | `cp.agt` | Два независимых измерения агентности; равенство кодов и автоматическое копирование запрещены |

> **Альтернатива для коучинга (без Activity Hub):** артефактный аудит даёт свидетельства для оценки уверенности: Git-репо, записи week-close/day-close, анализ речи, WP-контексты. Он не создаёт `cp.*` автоматически и не заменяет диагностический вопрос.

**Вычисление результата:**

```python
core_cp_fresh = all(cp_is_fresh(slice_code) for slice_code in CORE_CP)
cp_agt = cp.get('agt')
cp_agt_fresh = cp_agt is not None and cp_is_fresh('agt')
core_cp_floor = (
    min(cp[slice_code].baseline_idx for slice_code in CORE_CP)
    if core_cp_fresh else None
)
stage5_cp_gate_passed = (
    core_cp_fresh and core_cp_floor >= 4
    and cp_agt_fresh and cp_agt.baseline_idx >= 4
)
# При core_cp_floor >= 4 bottleneck ступеней ЛР отсутствует; cp.agt проверяется отдельно для 4→5.
bottleneck_slice = (
    None if not core_cp_fresh or core_cp_floor >= 4
    else argmin(cp[slice_code] for slice_code in CORE_CP)
)
stage5_transition_blocker = (
    'cp.agt' if core_cp_fresh and core_cp_floor >= 4
    and (not cp_agt_fresh or cp_agt.baseline_idx < 4) else None
)
skip_to_stage = min(core_cp_floor, 4) if core_cp_fresh else None

# cp.iwe и cp.cre — рекомендательные оси, не блокируют ступень.
# current_stage поступает из полного вычисления §5.2, поэтому свежий gate ступени 5
# даёт «Разработчик-3», а просроченный профиль не получает ложную текущую метку.
iwe_profile_stage = current_stage
iwe_master_stage = (
    'reassessment_required' if iwe_profile_stage is None
    else iwe_master_stage_label(iwe_profile_stage)
)
(expected_iwe, expected_cre) = (
    (None, None) if iwe_profile_stage is None
    else expected_profile(iwe_profile_stage)
)
iwe_fact_vs_expected = (cp.iwe, expected_iwe)
cre_fact_vs_expected = (cp.cre, expected_cre)

if skip_to_stage is None: recommended_stream = "reassessment_required"
elif skip_to_stage >= 4: recommended_stream = "S4"
elif skip_to_stage >= 3: recommended_stream = "S3"
elif skip_to_stage >= 2: recommended_stream = "S2"
else: recommended_stream = "S1"
```

Этот блок определяет размещение внутри базовых потоков ЛР. Ступень 5 впервые подтверждается только полным gate §5.2 и может быть достигнута в продвинутой траектории ЛР; при свежем полном gate действует `rr_readiness_status = ready`, а передача и старт РР оформляются отдельно. Один cp-профиль не может выдать ступень 5 в обход остальных условий.

**TTL:** `valid_until = assessed_at + 6 months` для четырёх стержневых срезов при любой текущей оценке; для `cp.agt` — только когда проверяется переход 4→5. Просроченный стержневой профиль даёт `stage_evaluation_status = indeterminate`, а не понижает `attained_stage`.

**Параметры переоценки (v5.1):**
- Кулдаун повторной диагностики: **7 дней** (ранее 30 дней в diagnose-iwe v4.x). Если профиль моложе 7 дней — показать текущий и предложить пройти заново; не запускать диагностику принудительно.
- Для ст.4+: `bottleneck_slice = None`. Все четыре стержневых среза ≥ 4 — разрыв между ними незначителен, bottleneck-концепция ступеней 1–4 теряет операциональный смысл. `cp.agt` проверяется отдельно как transition blocker (§6.1 Фаза 2). Старое имя runtime-поля `bottleneck_slot` требует отдельной миграции адаптера.
- Полный TTL профиля: 6 месяцев — без изменений.

*Источник изменений: WP-370 + commit 3a173605 FMT-exocortex-template 2026-06-18.*

### 6.2 Навигатор (MIM.R.007)

Использует bottleneck для квартального фокуса: цель = поднять baseline cp-bottleneck на +1 индекс.

### 6.3 Портной (MIM.SOP.001)

- Фокус-контент (квартал) = bottleneck одного из четырёх стержневых cp-срезов: cp.rhy, cp.wld, cp.skl, cp.int
- При подготовке 4→5 `cp.agt < 4` даёт отдельную рекомендацию по агентности, не меняя bottleneck и не понижая ступень 4
- cp.auto определяет канал доставки (глубина автопилота → тип контента)
- cp.int: ст. 3→4 расширение потенциала через M4 в ЛР; 4→5 — продолжение в продвинутой траектории ЛР с формированием готовности к РР

**Стадия мастерства IWE — функция ступени Ученика (не cp-индекса).** Source-of-truth:

| Ступень Ученика | Имя стадии мастерства IWE | Ожидаемый cp.iwe | Ожидаемый cp.cre |
|---|---|:---:|:---:|
| 1 Случайный | **Пользователь-1** | 1 | 0 |
| 2 Практикующий | **Пользователь-2** | 2 | 0 |
| 3 Систематический | **Пользователь-3 + Разработчик-1** (одновременно, переход) | 3 | 1 |
| 4 Дисциплинированный | **Разработчик-2** | 3+ (поддерживается) | 2 |
| 5 Проактивный | **Разработчик-3** | 3+ (передаётся другим) | 3 |

**Принцип лестницы:** на ст.1-2 человек осваивает пользование средой (ось управления — ведущая). На ст.3 — точка качественного перехода: одновременно достигает Пользователь-3 и начинает Разработчик-1. На ст.4-5 ведущая ось — создание (Разработчик-2 → Разработчик-3); пользование удерживается на уровне 3+ как фон.

**Что показывает Портной в персональном руководстве** (блок «Стадия мастерства IWE»):
- Имя текущей стадии (по ступени Ученика — из таблицы выше).
- Фактические cp.iwe и cp.cre (что измерил Диагност).
- Дельта от ожидания: если cp.iwe или cp.cre ниже ожидаемого → подсветить «что подтянуть».

**Логика рекомендаций Портного:**

1. Если фактический cp.iwe ниже ожидаемого для ступени → контент по освоению ритуалов (Day Open/Close, Week Close, маршрутизация).
2. Если cp.cre = 0 на ст.3+ → контент по начальной кастомизации среды (settings, первые Pack-разделы, extension-файлы) как вход в роль Разработчика-1.
3. Если cp.cre ниже ожидаемого на ст.4-5 → контент по углублению создания (Pack-домены, MCP-инструменты, расширения).
4. Если профиль соответствует или опережает ожидание → контент следующей стадии или фундаментальное расширение (cp.wld, cp.int).

**cp.iwe и cp.cre не блокируют ступень Ученика** — это рекомендательные оси. Ступени 1–4 определяются двойным RCS-gate (§5.1); ступень 5 дополнительно требует полного gate Проактивного (§5.2), независимо от того, началось ли РР.

### 6.4 Оркестратор (WP-203)

Видит полный cp-профиль + bh-метрики (§12). Триггеры корректировки дня:
- Резкое отклонение bh.sys от нормы → защитная реакция (восстановление ритма)

## 12. MVP: Автоматический расчёт ступени (bh-характеристики, WP-310)

> **Статус:** v4, май 2026 (WP-310 Ф1-Ф9). 7 bh-характеристик из событий Activity Hub — автоматический сигнал Аттестатора. Он не заменяет Диагноста и не создаёт cp-значения; итог ступеней 1–4 всегда требует композиции §5.1.
>
> **Кодирование:** `bh.` = behaviour (поведенческие метрики из событий). `cp.` = capacity (потенциал через рубрики Диагноста). Старые коды S/T/M/W/A → bh.sys/bh.inv/bh.met/bh.awr/bh.agn.
>
> **Весовая конфигурация:** `DS-ecosystem-development/…/Data-Governance/iwe-actions-catalog.md §7`.

### 12.1 Модель 7 bh-характеристик

| Код | Характеристика | Ось | Тип | Показатель |
|-----|----------------|-----|-----|------------|
| **bh.sys** | Систематичность | Мастерство | обязательная | `self_dev_days_per_week` — среднее дн/нед в скользящем окне |
| **bh.inv** | Инвестиционность времени | Мастерство | обязательная | `avg_hours_per_week` — среднее ч/нед (slot_logged + lesson_completed) |
| **bh.met** | Методичность | Мастерство | компенсаторная | `methodical_events_per_month` — применение методов, событий/мес |
| **bh.awr** | Осведомлённость | Мировоззрение | основная | `worldview_score` — взвешенная сумма событий рефлексии за 30 дней |
| **bh.agn** | Агентность | Мировоззрение | основная | `agency_score` — взвешенная сумма самоинициированных событий |
| **bh.scl** | Масштабность | Мастерство | информационная | `scale_score` — РП с фактическим временем (wp_completed × actual_hours) |
| **bh.stb** | Устойчивость | Мастерство | gate | `max_gap_days` — максимальный разрыв без подтверждённого `practice_day` |

> **Различение типов.** «Обязательная» = ноль блокирует ступень. «Компенсаторная» = низкое не блокирует при компенсации. «Основная» = наибольший вес в оси Мировоззрения. «Gate» = срабатывает как дополнительный порог при расчёте ступени.

### 12.2 Показатели и рубрики

#### bh.sys — Систематичность

**Смысл:** регулярность именно саморазвития. `git_commit`, `wp_created`, `coding_time` — рабочая активность, не считается.

**Принцип окна:** растёт со ступенью. Проактивный оценивается за 24 нед — нужно доказать устойчивость на дистанции.

**Множество содержательных событий `SELF_DEV_EVENT_TYPES`** (полный реестр в `iwe-actions-catalog.md §0`):
```
lesson_completed, knowledge_extracted, pack_updated, qualification_granted,
strategy_session_completed, iwe_session
```

Это множество применяется для семантической классификации событий, но **не является источником дней практики**. `day_plan_opened`/`day_open`, `day_plan_closed`/`day_close`, `week_plan_closed` и `month_plan_closed` — ритуальные маркеры входа/закрытия; они явно не входят в `SELF_DEV_EVENT_TYPES` и сами по себе не создают день практики.

**Единственный источник `practice_day` для `bh.sys` и `bh.stb`:** подтверждённое событие `learning.domain_event` с `activity_domain IN ('practice', 'learning')`, причём `event_type NOT IN RITUAL_MARKER_EVENT_TYPES`. День считается один раз по календарной дате независимо от числа событий. Это реализует D.146 и согласовано с Event Model PD.FORM.095: маркер может сопровождать практику, но не заменяет её.

| Индекс | Ступень-аналог | Порог дн/нед | Окно |
|--------|:---:|:---:|:---:|
| **0** | — | < 1 | — |
| **1** | Случайный | ≥ 1 | 1 нед |
| **2** | Практикующий | ≥ 3 | 4 нед |
| **3** | Систематический | ≥ 5 | 8 нед |
| **4** | Дисциплинированный | ≥ 6 | 12 нед |
| **5** | Проактивный | ≥ 6.7 | 24 нед |

> **6.7 дн/нед = 1 день пропуска в месяц.** Достижимо для Проактивного с ежедневной практикой.

#### bh.inv — Инвестиционность времени

**Источники (К4 fix):** только `slot_logged.hours` + `lesson_completed.duration_minutes/60`.

> **К4 (WP-310):** `coding_time` (WakaTime) исключён — он включает все репозитории, в том числе рабочие. Используются только чистые учебные события. Нормативы установлены с учётом занижения этих источников.

**К4-uplift (Ф13, 15 мая):** `slot_logged` принимает `payload.source` ∈:
- `active` — вручную через `/slot N` после реальной практики
- `self_report_backfill` — одноразовый onboarding-ввод среднего времени за прошлый период
- `self_report_daily` — ответ на Day Close prompt (если slot за день = 0)
- `self_report_weekly` — ответ на Week Close prompt (catch-all)

Все четыре источника равноценны для bh.inv. `coding_time` остаётся исключённым — он мерит ВСЕ репо, не декларирует учёбу. Self-report допустим, потому что декларация явна и осознанна.

**bh.sys и bh.stb НЕ ВКЛЮЧАЮТ self_reported события или ритуальные маркеры.** Только подтверждённая доменная активность по правилу `practice_day` выше. Self-report подтверждает ВРЕМЯ, не регулярность — иначе мы инфлируем оба показателя из одного ввода.

**Правка истории:** UPDATE `payload.hours` существующего события (overwrite, MVP). Корректирующие события (immutable event log) — backlog при необходимости audit-trail.

| Индекс | Ступень-аналог | Порог ч/нед | Окно |
|--------|:---:|:---:|:---:|
| **0** | — | < 0.5 | — |
| **1** | Случайный | ≥ 0.5 | 1 нед |
| **2** | Практикующий | ≥ 4 | 4 нед |
| **3** | Систематический | ≥ 6 | 8 нед |
| **4** | Дисциплинированный | ≥ 10 | 12 нед |
| **5** | Проактивный | ≥ 10 | 24 нед |

#### bh.met — Методичность

**Показатель:** `COUNT(events за 30 дней)` из: `lesson_completed`, `knowledge_extracted`, `pack_updated`, `qualification_granted`.

| Индекс | Диапазон |
|--------|----------|
| **0** | 0 |
| **1** | 1–3/мес |
| **2** | 4–10/мес |
| **3** | 11–25/мес |
| **4** | 26–50/мес |
| **5** | > 50/мес |

#### bh.awr — Осведомлённость (worldview score)

**Окно:** 30 дней (З4, WP-310 — явно зафиксировано в `AWR_WINDOW_DAYS = 30`).

**Показатель:** взвешенная сумма событий рефлексии за 30 дней → индекс 0–5. Веса: `iwe-actions-catalog.md §7`.

| Индекс | Операционные признаки |
|--------|----------------------|
| **0** | Рефлексий нет |
| **1** | Единичные рефлексии |
| **2** | Начинает видеть паттерны. Системный язык — эпизодически |
| **3** | Регулярные рефлексии (Week Close / Month Close). Различает роли, методы |
| **4** | Чёткий системный язык. Видит себя как деятеля в системах |
| **5** | Формирует системное видение у других |

#### bh.agn — Агентность

**Показатель:** взвешенная сумма за 30 дней → индекс 0–5. Веса: `iwe-actions-catalog.md §7`.

| Индекс | Операционные признаки |
|--------|----------------------|
| **0** | Нет инициированных действий |
| **1** | 1–2 самоинициированных действия/мес |
| **2** | Несколько, есть хотя бы 1 самостоятельный РП |
| **3** | ~50% задач из собственных целей. 1–2 активных РП |
| **4** | Несколько независимых РП. Действует в неопределённости |
| **5** | Формирует повестку для ближнего круга |

#### bh.scl — Масштабность

**Показатель:** `SUM(actual_hours по wp_completed за 30 дней)` → взвешенная сумма → индекс 0–5.

> **К2 fix (WP-310):** bh.scl должен мерить фактически отработанное время по РП (actual_hours из payload wp_completed), а не бюджет заявленный при создании. Без поля `actual_hours` в событии — используется фиксированный вес, что является приближением. Тикет на добавление поля: WP-214 Ф11.

**Информационная характеристика** — не блокирует ступень в текущем MVP. Используется Навигатором для оценки «масштабности деятельности» учеников на ст.3+.

#### bh.stb — Устойчивость

**Показатель:** максимальный разрыв без подтверждённого `practice_day` (в днях) за учётный период ступени.

> **bh.stb ≠ bh.sys.** bh.sys = средняя частота (сколько дней из семи). bh.stb = худший разрыв (самый длинный простой). Оба нужны: высокое bh.sys с одним разрывом-3-недели = высокая bh.sys, но низкое bh.stb.

**Нормализация bh.stb:**

| bh.stb индекс | Макс. разрыв | Ступень-аналог |
|:---:|:---:|:---:|
| **5** | ≤ 1 день | Проактивный |
| **4** | 2–3 дня | Дисциплинированный |
| **3** | 4–7 дней | Систематический |
| **2** | 8–14 дней | Практикующий |
| **1** | 15–30 дней | Случайный |
| **0** | > 30 дней | — |

**STB_GATE** (минимальный bh.stb для получения ступени): ст.2 ≥ 1, ст.3 ≥ 2, ст.4 ≥ 3, ст.5 ≥ 4.

**Алгоритм расчёта** (источник — этот раздел; зеркало в `stage_config.py::compute_stage_mvp`):

```
compute_stage_mvp(s, t, m, w, a, total_hours, stb) → recommended_stage ∈ {1..5}

  s=bh.sys, t=bh.inv, m=bh.met, w=bh.awr, a=bh.agn — индексы 0–5.
  total_hours — накопленные ч (только slot_logged + lesson_completed, К4).
  stb=bh.stb — индекс устойчивости (max-gap).

  Gates в порядке:
  1. Mandatory: s==0 или t==0 → ступень 1
  2. Матрица минимумов (выше): все 5 bh ≥ минимумов → bh-кандидат
  3. Hard gate накопленных часов: total_hours < min[кандидат] → кандидат−1
  4. bh.stb gate: stb < STB_GATE[кандидат] → кандидат−1
```

> Для ступеней 1–4 результат этой функции — только `recommended_stage`; подтверждённая текущая оценка появляется лишь после полного недельного окна bh-наблюдений и равна `min(recommended_stage, core_cp_floor)` при свежем стержневом профиле (§5.1). Значение 5 означает лишь `stage5_bh_gate_status = passed` и требует также `stage5_cp_gate_status = passed`, `form093_metric_gate_status = passed` и `form093_real_change_gate_status = passed` (§5.2). Фактический старт РР проверяется отдельно.

### 13.1 Каталог характеристик

Девять характеристик оси Компетентности (mastery), состав не является инвариантом модели — может расти/меняться решением пилота. Каждая раскрывается через аспекты; аспект — не независимый счётчик, а уточнение характеристики (правило «один индикатор — один дом»).

| Характеристика | canonical_id | Определение (одна строка) | Тип (личностная/средовая) | В формуле ступени (§13.3) |
|---|---|---|---|---|
| Собранность | `собранность` | Организует и удерживает свою деятельность (внимание, состояние, время) в работе и во времени | личностная | обязательная |
| Агентность | `агентность` | Определяет направление деятельности, принимает решения, инициирует изменения с учётом последствий | личностная | обязательная |
| Мировоззренческая зрелость | `зрелость` | Проработанность представлений о себе/мире/развитии, проявленная в основаниях решений | личностная | обязательная |
| Системность | `системность` | Рассматривает и изменяет объекты деятельности через системные описания | личностная | обязательная |
| Оснащённость | `оснащённость` | Наличие, пригодность и работоспособность средств деятельности | средовая | обязательная |
| Ясность | `ясность` | Интеграция мировоззрения и системного мышления в рабочий артефакт (не воспроизведение терминов) | личностная, gate в `PD.FORM.093` | обязательная |
| Продуктивность | `продуктивность` | Ценность, производимая в единицу времени | личностная, supporting в `PD.FORM.093` | вспомогательная |
| Ресурсность | `ресурсность` | Умение мобилизовать доступные ресурсы для деятельности | личностная, supporting в `PD.FORM.093` | вспомогательная |
| Стрессоустойчивость | `стрессоустойчивость` | Выдерживает нагрузку без срыва практики | личностная, supporting в `PD.FORM.093` | вспомогательная |

**Уточнение вокабуляра (найдено независимой проверкой 14.09).** «Обязательная/вспомогательная» — деление ЭТОЙ модели по участию в формуле ступени (§13.3), своя ось, не переиспользует термин «gate» из `PD.FORM.093` (который про другую лестницу — переход 4→5 к степени квалификации, §5.4 того документа). У ясности термины совпадают по факту (gate там же, обязательная здесь), но это совпадение, не тождество понятий — сверено отдельной колонкой, не смешано в одной.

**Омонимия «Оснащённость».** Ось состояния платформы `belonging` (тир T0-T4) называется тем же словом — другая сущность (что система знает о пользователе), не характеристика. Пилот 13.09 отклонил переименование характеристики (слово уже прозвучало перед живой когортой практикума «Собранность», установочная встреча 13.09) — сущности разводятся контекстом употребления, не именем.

**Структура измерения (по FORM.088 §2, «квартет»).** Каждая характеристика — и v5-каталога, и этого раздела v6 — измеряется четвёркой: характеристика / показатель / значение (сейчас + baseline) / потенциал (текущий потолок шкалы для человека). Элементы «характеристика/показатель/значение» сохраняются без изменений (см. §13.2); элемент «потенциал» (персональный потолок шкалы) для четырёх новых характеристик (ясность, продуктивность, ресурсность, стрессоустойчивость) **не формализован** — открытый пункт §13.7 п.2.

**Обязательные и вспомогательные характеристики.** Не все девять входят в формулу ступени (§13.3) одинаково. **Обязательные (участвуют в `min_личн`/`v2`):** собранность, агентность, зрелость, системность, ясность (личностные) + оснащённость (средовая) — шесть характеристик, по образцу существующего в `PD.FORM.093` разделения gate/supporting (см. колонку в таблице выше). **Вспомогательные:** продуктивность, ресурсность, стрессоустойчивость — читаются той же единой точкой чтения, что и обязательные (контракт «витрины», §13.7 п.4), отслеживаются наравне с остальными, но **не входят в расчёт `stage_v6`** и не блокируют его через `dormant-no-source`. Это прямое следствие того, что две из трёх (ресурсность, стрессоустойчивость) сегодня без источника (§13.2) — при обратном решении («все девять обязательны») формула была бы невычислима постоянно, что и было бы честной причиной её не вводить вовсе.

#### 13.1.1 Аспекты собранности

- **В конкретной работе:** внимательность, концентрация, управляемость переключений, организация состояния и режима.
- **Во времени:** систематичность (обобщающий аспект воспроизводимости практики); регулярность, ритмичность, восстановление после перерывов — уточнения систематичности, не отдельные счётчики.
- **В результате** (новый аспект, добавлен 13.09): доведение до результата — закрывает начатое артефактом, не бросает на середине. Переиспользует те же поведенческие сигналы, что и остальные аспекты «во времени» (учёт и вклад времени, устойчивость практики), не заводит новый счётчик. **Обоснование границы — структурное, не техническое** (см. §13.1.6): этот аспект самостоятельно оправдан внутри модели ступени, независимо от состояния соседней характеристики другой лестницы. Операциональная оговорка о частичном пересечении сигналов со сломанной формулой другой лестницы — в §13.2, не здесь: здесь граница онтологическая, там — честность источника.

Границы: собранность ≠ агентность (агентность — вектор, собранность — удержание движения по вектору, Kimi раунд 1). Собранность ≠ оснащённость (мастерство использования средств vs их наличие).

#### 13.1.2 Аспекты агентности

Самостоятельность целеполагания, инициативность, автономность решений, ответственность за решения, коррекция направления, масштаб инициируемых изменений. Агентность ≠ «всё сам» — осмысленно принятая чужая цель и делегирование ИИ тоже агентность; критерий — кто принял решение и на каком основании.

**Консолидация (13.09).** `cp.agt` (диагностический срез), `agency_idx` (авторасчёт по событиям), `CHR.K.001` (общий каталог характеристик) — один и тот же объект, определения сведены. `MIM.M.004` (шкала делегирования по степеням квалификации) — качественно другое (распределение ответственности во внешней квалификационной лестнице, не личная агентность), переименовано в «делегирование», в каталог не входит.

**Открытый пункт (не блокер Ф2).** Третья, более широкая формализация — `PD.FORM.113` (желание+возможность+ответственность, кластер «Элита», масштаб до человечества, не подключена к gate-конвейеру). Действующая gate-агентность (`cp.agt`/`agency_idx`, используется в `PD.FORM.108` — gate ≥4 на входе в «Рабочее развитие») — узкая версия, только «самоинициация в проектах». Обе формализации существуют параллельно осознанно; сверка терминов — отдельная задача, не блокирует эту правку.

#### 13.1.3 Аспекты мировоззренческой зрелости

Осмысленность убеждений, обоснованность, согласованность, готовность пересматривать при новых свидетельствах, связь представлений с деятельностью, рефлексия пути. Только диагностические свидетельства — количество событий рефлексии зрелость не присваивает.

#### 13.1.4 Аспекты системности

Владение системными различениями, построение моделей, работа со связями и уровнями, учёт динамики и последствий. Центральный аспект — применение системного описания к решению (обосновал выбор, назвал влияние и ограничения, проверил последствия), не наличие разбора самого по себе.

#### 13.1.5 Аспекты оснащённости

Функциональное покрытие, информационная оснащённость, связанность средств, доступность и надёжность, управляемость. Реляционная характеристика «исполнитель-среда» — свойство условий, не внутренняя способность.

Граница с агентностью/системностью: наличие/пригодность/работоспособность средств → оснащённость; умение создавать средства и управлять средой → агентность/системность; мастерство использования среды в работе → собранность.

Граница с ресурсностью (§13.1.6): оснащённость = наличие нужных средств (пассивное состояние); ресурсность = умение их мобилизовать (активное качество).

#### 13.1.6 Ясность, продуктивность, ресурсность, стрессоустойчивость

Импортированы из `PD.FORM.093` (§3.2 «Карточки 8 характеристик» — ясность карточка 1, продуктивность/ресурсность/стрессоустойчивость карточки 6-8; решение пилота 13.09) как отдельные характеристики каталога, не сливаются с существующими (в частности ясность отдельна от зрелости/системности — про сведение обоих в конкретный результат прямо сейчас, не про основания или инструмент по отдельности). Ссылка «§2.6-2.9» в более ранних записях этого решения (карточка `WP-576`) относится к нумерации концепт-документа сессии, не к самому `PD.FORM.093` — уточнено независимой проверкой 14.09.

Ясность — gate-характеристика перехода 4→5 в `PD.FORM.093` (сводная таблица §3.1, composition rule §5.4; baseline ≥4). Продуктивность/ресурсность/стрессоустойчивость — supporting (baseline-ориентир ≥3, просадка не блокирует переход, требует индивидуального плана).

**«Способность производить» — не входит в этот каталог (структурная граница, не техническая).** `PD.FORM.093` определяет отдельную gate-характеристику «способность производить» (доводит ли работу до артефакта вообще — бинарный оттенок 0-5 по числу доведённых работ; ось «есть/нет результата»). Продуктивность — другая ось, «сколько ценности за час» — они измеряются не на одном интервале и не сравниваются напрямую. «Способность производить» гейтит степень квалификации (внешнюю лестницу, §13.4), не ступень RCS этого документа. **Решение (уточнено раундом критики 13.09): она не входит в каталог ступени ПОТОМУ, ЧТО принадлежит другой лестнице — не потому, что её формула сегодня сломана.** Факт «`production_capacity_idx` в проде всегда 0 (баг коллектора, передан в WP-7)» — это диагноз кода, не онтологическое основание; если баг починят, характеристика останется характеристикой степени квалификации, а не переедет в этот каталог автоматически.

Отдельно от этого решения — аспект «в результате» собранности (§13.1.1) **самостоятельно обоснован внутри модели ступени**: доведение начатого до артефакта — законная грань собранности как таковой. То, что его сигналы (`bh.inv`, `bh.met`) частично совпадают с сигналами сломанной формулы «способности производить», не делает один аспектом другого — это два независимых обоснования, которые опираются на пересекающиеся, но не тождественные данные, что допустимо между разными лестницами.

### 13.2 Источники и честность измерения

Для каждой характеристики — явный источник: авто-событие / диагностическое задание / самоопросник / нет источника. ### 13.3 Ступень: согласованный профиль

> **АрхГейт обязателен перед первым кодом**, реализующим это правило (стейдж-эвалюатор, матрица минимумов §12.3 v5) — смена алгоритма присвоения ступени системного уровня. Правка Pack-формализации ниже гейта не требует. **Эта правка не меняет runtime: `check_rcs_stage()` остаётся единственным действующим расчётом до отдельной кодовой миграции.**

**Формула.** Профиль = оценки ОБЯЗАТЕЛЬНЫХ характеристик текущего состава (целые 1-5; состав обязательных — §13.1, сегодня 6 из 9: собранность, агентность, зрелость, системность, ясность, оснащённость). Вспомогательные (продуктивность, ресурсность, стрессоустойчивость) в формулу не входят — видны отдельно на витрине (§13.7 п.4). Отсортировать оценки обязательных по возрастанию: v1≤v2≤…≤vn (n=6 сегодня, меняется вместе с составом обязательных). `min_личн` = минимум среди личностных обязательных характеристик (все обязательные, кроме средовых — сегодня средовая одна: оснащённость).

```
stage_v6 = min( v2 , min_личн + 1 )
```

Формула определена одинаково при любом составе обязательных характеристик — не фиксирует конкретное число n, но её ЗНАЧЕНИЕ зависит от состава (вторая по возрастанию оценка `v2` и `min_личн` меняются при добавлении/удалении обязательной характеристики). Тотальна (определена для любого профиля из ≥2 обязательных характеристик), монотонна (не убывает при росте любой оценки). Крайний случай `n < 2` обязательных характеристик (если состав когда-нибудь сократится) формулой не покрыт — отдельное решение при таком сокращении состава, не покрывается этой версией.

Примеры (шесть обязательных, именованных — оснащённость обозначена отдельно как единственная средовая):
- собранность=3, агентность=3, зрелость=5, системность=5, ясность=5, оснащённость=3 → `v2=3`, `min_личн=3` → **stage_v6=3**
- собранность=3, агентность=3, зрелость=3, системность=3, ясность=5, оснащённость=3 → `v2=3`, `min_личн=3` → **stage_v6=3**
- собранность=1, агентность=5, зрелость=5, системность=5, ясность=5, оснащённость=4 → `v2=4`, `min_личн=1` → **stage_v6=2**
- собранность=4, агентность=4, зрелость=4, системность=4, ясность=4, оснащённость=1 → `v2=4`, `min_личн=4` (оснащённость средовая, не входит в `min_личн`) → **stage_v6=4**, одна низкая средовая не блокирует
- собранность=2, агентность=4, зрелость=4, системность=4, ясность=4, оснащённость=1 → отсортировано [1,2,4,4,4,4] → `v2=2`, `min_личн=2` → **stage_v6=2**, средовая + личностная одновременно низкие блокируют честно (исправлено независимой проверкой 14.09 — было ошибочно указано `v2=4`, скопировано из предыдущего примера; итоговое значение 2 было верным и раньше, промежуточное число — нет)

**Согласованность — флаг, не блокер.** Разброс `vn−v1 ≥ 3` → профиль «рассогласован»: это диагностический вывод (не отдельная ступень), понижает confidence, отстающая характеристика становится приоритетом роста (наследник bottleneck). Ступень не отнимается за рассогласованность.

**Gate агентности 4→5.** Ступень 5 (Проактивный) дополнительно требует агентность ≥4. На ступенях 1-4 агентность участвует наравне со всеми характеристиками, отдельного порога нет.

**Дыры данных — жёсткое правило, не смягчение confidence.** Нет сигнала по ОБЯЗАТЕЛЬНОЙ характеристике (`needs_refresh`, состав — §13.1) → `stage_v6 = null` до дозаполнения, а не расчёт с пониженной уверенностью. Действующей остаётся ступень v5 (см. `rcs_version`, §13.6). Не подставлять вымышленные значения, не маскировать заниженной точностью. (Уточнено раундом критики 13.09 — прежняя формулировка «пониженная confidence» в §13.6 не должна пониматься как альтернатива этому правилу, она про доверие к УЖЕ ПРИСВОЕННОЙ ступени, не про присвоение при дыре в обязательных данных.)

**Частичный профиль при `stage_v6 = null` (уточнено раундом критики 13.09, п.4).** `stage_v6 = null` не означает пустой профиль на витрине: каждая ОБЯЗАТЕЛЬНАЯ характеристика показывается своим значением или явным `null` по отдельности (какая именно характеристика создала дыру — видно), плюс все три вспомогательные — независимо от статуса `stage_v6`. Витрина не обязана «прятать» всё при отсутствии итоговой ступени; прячется только сам вывод ступени.

**Стрессоустойчивость вне обязательных характеристик — не случайность.** Она уже `dormant-no-source` (§13.2) и отнесена к вспомогательным (§13.1) именно поэтому — если бы она была обязательной, `stage_v6` был бы null постоянно, у всех, что равносильно отказу от формулы. Тот же аргумент подтверждает решение по ресурсности.

**Р1 (решение пилота 13.09, статус: зафиксировано, не реализовано).** Новая формула заменит `check_rcs_stage()` при реализации сразу, без отдельного **пользовательского** параллельного поля `stage_vnext` (видимого людям, живущего в БД как второй расчёт рядом с боевым на протяжении недель) и без формального этапа сравнения на реальных профилях как **отдельного decision-gate перед переключением**. После АрхГейт и в рамках Ф3 (`WP-576`) реализация v6 атомарно переключает алгоритм; до развёртывания единственным действующим расчётом остаётся v5. Расхождения ловятся живой приёмкой на фазе каскада, не отдельным decision-gate ДО переключения — это решение о порядке работ и об объёме пользовательской поверхности, не отказ от обычной инженерной проверки. **Уточнение (независимая проверка 14.09, снимает найденное противоречие с картой каскада):** shadow/test-прогон нового расчёта на исторических данных ПЕРЕД переключением — стандартная инженерная практика при любой замене вычисления, не то, что отклоняет это решение; отклонён именно `stage_vnext` как отдельный долгоживущий параллельный путь с собственным decision-gate поверх него.

**Р2 (решение пилота 13.09, статус: deferred — формула ещё не правлена) — сужение формулы регулярности `PD.FORM.093 §5.2` (карточка 4, `regularity_idx`) относительно gate-вычисления перехода 4→5 (§5.4).** **Основание решения уточнено независимой проверкой 14.09 — исходная формулировка называла источником пересечения слагаемое `cp.skl`, которого в формуле регулярности нет вообще (оно в собранности, способности производить и продуктивности, §5.2 карточки 3/5/6); ниже — реальное основание.** «Регулярность» (§5.2 карточка 4) и «собранность» (§5.2 карточка 3, `composure_idx`) используют один и тот же auto-композит на входе — часы в неделю на методах саморазвития (WakaTime/LMS) и регулярность слот-планирования (`day_open_completed`/`day_close_completed`) — различаясь в основном окном наблюдения (собранность — короче, регулярность — явно 12 недель) и одним дополнительным элементом у регулярности (серия недель 4-недельной автономии, `wp_created.initiator=self` без внешних триггеров). Решение: сузить регулярность до элементов, которых нет у собранности (окно 12 недель + автономный ряд), не пересчитывая пороги перехода 4→5 и не сливая характеристики. **Это переопределение понятия, не только формулы:** регулярность в `PD.FORM.093` ранее означала «то же, что собранность, плюс более длинное окно», после правки будет означать «устойчивость и автономность на длинном горизонте», не дублируя входные сигналы собранности. Порог `≥4` и структура gate-вычисления §5.4 сохраняются. Правка формулы физически вносится в `PD.FORM.093 §5.2` отдельным коммитом — этот пункт фиксирует решение и его (исправленное) обоснование для обоих документов, актуальная формула до той правки не меняется.

### 13.4 Три лестницы — не путать

Модель считает только **ступень** (эта, §13.3, 5 значений, статус draft/`not_implemented` до Decision Gate/АрхГейт реализации). Не то же самое, что:
- **Степень квалификации** (8 значений, Ученик→Революционер, присваивается ВНЕШНЕ методсоветом — защита + деятельность + решение комиссии, не расчётом). Gate-характеристики этой лестницы (включая «способность производить», §13.1.6) в каталог ступени не входят.
- **Охват изменений** (отдельная шкала 1-6, используется как gate перехода 4→5 в `PD.FORM.093`).

Путаница между лестницами регулярно встречается в источниках (найдено разведкой 13.09) — характеристика «способность производить» (§13.1.6) была кандидатом именно на эту путаницу: она гейтит степень квалификации, не ступень.

### 13.5 Каскад «внимание — мировоззрение — мастерство — системы»

Объяснительная проекция (не формальная привязка каждой колонки к характеристике — решение пилота 13.09, снимает нерешаемый вопрос «куда девать колонку Мастерство»). Читается по практикумам: S1 «Собранность» крепит Внимание, первый заход — в Мировоззрение; S2 «Агентность» крепит Мировоззрение, первый заход — в Мастерство; S3 «Системность» крепит Мастерство, первый заход — в Системы. Рост не переключается, а накапливается — ничего не выключается по пути, ступень подтверждается по всем характеристикам сразу, не по одной.

Разрыв «имя практикума ≠ его фактический фокус» (практикумы S1/S2 по канону `WP-385` фактически целят в `cp.wld`/`cp.skl`) существовал до этой модели — живая презентация практикума «Собранность» (13.09) показывает это как осознанный кумулятивный дизайн, не как ошибку.

### 13.6 Версионирование и обратная совместимость

- `rcs_version`: `v5.0` (§1-12, действующие расчёты) и `v6` (этот раздел, `not_implemented`) сосуществуют. Существующие записи `cp_assessments` НЕ переписываются; v6-оценка — новая запись с полями `source_assessment_id`, `source_rcs_version='v5.0'`, `derivation_version='v6.mig.1'`, `derived_at`.
- **Переименования и консолидации** (например агентности, §13.1.2) — только через слой `canonical_id`+`alias_name`. **Механизм (выбран раундом критики 13.09, вариант «таблица-сателлит», не `registry-view` — второй вариант отклонён, чтобы не создавать неоднозначность реализации): не аддитивные nullable-поля в существующей `learning.characteristic_norm`** (это всё равно изменение схемы действующей таблицы + backfill), **а отдельная физическая таблица-сателлит** вида `(catalog_version, canonical_id, alias_name, legacy_key)`. Минимальные требования к её схеме до кода (уточнено раундом критики, финальный проход): первичный ключ строки `(catalog_version, canonical_id, alias_name)` даёт идентичность записи; отдельно **`UNIQUE (catalog_version, alias_name)`** — это и есть правило «один alias резолвится ровно в один canonical_id на версию каталога» (составного ключа выше для этого недостаточно — он не запрещает записать один и тот же alias с разными canonical_id). Правило кратности в другую сторону: один `canonical_id` может иметь несколько `alias_name` (например агентность: `cp.agt`, `agency_idx`, `CHR.K.001`) — это разрешено обеими схемами ключей. Записи версии `catalog_version` иммутабельны после публикации (новая консолидация — новая версия, не правка задним числом). Существующие читатели (`dt_calc.py`, `cp_assessment.py`) продолжают читать по старым ключам без изменений до отдельного решения о переключении; таблица-сателлит — это отображение поверх, не миграция первичных данных. Честная оговорка: это backward-compatible ROLLOUT, не гарантия «вообще без schema change» — переключение первичного ключа, uniqueness/FK или контрактов API на canonical-id, если оно понадобится, останется отдельным, потенциально breaking, решением на фазе реализации.
- Детерминированный derive-проход: `cp_scores` + bh-метрики → v6-профиль с полем confidence по каждой присвоенной характеристике. Confidence — про доверие к уже присвоенному значению (свежесть источника и т.п.); при отсутствии сигнала по обязательной характеристике действует отдельное, более жёсткое правило §13.3 (`stage_v6 = null`, не «низкая confidence»).
- Двойной gate Аттестатор→Диагност (§5.1-5.2 v5) сохраняется и проверяет профильный паттерн (разброс, хвост), не только ступень.
